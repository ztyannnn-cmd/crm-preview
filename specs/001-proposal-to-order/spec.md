## Clarifications

### Session 2026-10-19

- Q：审核报价和成单金额是否采用所列完整规则？ → A：用户选择“采用整组规则，负Margin提示但不拦截（推荐）”。未通过须写原因，原记录可补说明复审或明确结束，复审不限次、不自行换审核人；运营实质方案变更回审、PM自提免审，保持已确认条数补正规则。正式报价不限轮，登记客户还价/正式提交达人回价后立即移交对应负责人。订单取最终有效达人价与客户接受价，同币种、最多两位小数、总额均大于0；默认均分且余分按视频顺序补齐，可按职责手动拆分且合计一致；负Margin提示不拦截；一提报一单，成单保留记录锁定普通改价，不新增撤回/纠错流程。

- Q：是否采用所列必填、本人草稿、单份在途与再次合作规则？ → A：用户选择“采用整组规则（推荐）”。正式字段见 FR-004；草稿按本人＋达人＋项目唯一、不同人可各存；同达人同项目最多一份未成单且未结束正式提报；结束未成单后原负责人可新提，成交后仅当前唯一负责人可再次合作，旧视频未验收不阻止，归属不明确先处理归属。

- Q：除 PM 自提外，是否采用运营/审核 PM/直属 PM 分工及管理员不代业务？ → A：用户选择“采用上述分工，管理员不代业务（推荐）”。负责运营管理本人记录及达人价、确认达人并建单；审核 PM 管理分配审核、客户价与客户反馈；直属 PM 只读直属业务及双方金额；其他同事不看他人业务明细；用户指定的测试管理员管理身份/角色/项目分配并可查全部测试业务，不代提报、审核、报价或建单。

- Q：PM 自提由谁继续负责、报价填写后何时可建单？ → A：用户确认 PM 本人负责到最终视频验收；填写双方报价后先待正式对客报价，客户接受、达人确认后才可建单。用户另授权排查无阻碍后直接更新代码；本次按该授权实施，不代表整体业务规格已经确认。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 运营提交可交接审核的提报 (Priority: P1)

运营提报走审核路径（已确认角色分工）；PM 可以提报自己的达人，免提报审核，直接填双方报价（已确认）。PM 本人继续负责成单及后续最终视频验收（已确认）。
**Why this priority**: 提报是本轮业务入口，资料和归属错误会影响后续报价及成单。
**Independent Test**: 使用独立运营与 PM 身份，仅完成提报和审核可见性检查，无需推进交付。
**Acceptance Scenarios**:

1. **AC-01 Given** 已授权运营 A，**When** 保存不完整草稿并退出后重新登录，**Then** 原填写内容可恢复，未产生正式提报或审核待办（FR-002/003）。
2. **AC-02 Given** 完整提报，**When** A 正式提交，**Then** 生成唯一可追踪提报编号，审核 PM 可读取；保留提交时资料与操作人，草稿不再可覆盖该提报（FR-004/005）。
3. **AC-03 Given** 缺邮箱或总价为 0 的提报，**When** 提交，**Then** 按最终确认的必填规则拒绝并定位字段，保留填写内容，无正式记录残留（FR-004/016）。
4. **AC-04 Given** 同达人同项目已有草稿、在途提报或历史订单，**When** 再次发起，**Then** 不同人可各存本人草稿；有未成单且未结束正式提报时拒绝再提交；历史结束/成交后的重提按下方已确认矩阵处理，不覆盖旧记录、不泄露无权查看的报价（FR-003/006）。
5. **AC-25 Given** 正式提报，**When** 逐一缺少 FR-004 必填项、数量0或101、达人总价非正，或 PM 自提对客价草稿非正，**Then** 拒绝正式提交、指出字段并保留输入；权益/备注为空仍可提交，草稿允许不完整（FR-003/004）。
6. **AC-26 Given** 同达人同项目历史记录，**When** 发起新轮次，**Then** 已结束未成单允许原负责人新提；已有成交允许当前唯一负责人在无在途正式提报时新提，即使旧视频未验收；非负责人、归属不明及已有在途的重复提交被拒绝（FR-006）。

### User Story 2 - PM 审核并与运营完成报价协作 (Priority: P1)

运营提报由审核 PM 处理审核及客户侧报价（已确认），运营登记达人价；PM 本人提报自己的达人时免提报审核，直接填达人价和对客价（已确认）。
**Why this priority**: 双方金额与审核结果决定能否成单。
**Independent Test**: 使用已提交的隔离提报，分别执行通过、未通过、客户还价及达人回价，无需创建订单。
**Acceptance Scenarios**:

1. **AC-05 Given** 待审核提报，**When** 审核 PM 通过并保存对客报价草稿，**Then** 显示下一待办，草稿不冒充已正式报价；正式提交才新增报价记录（FR-007/009）。
2. **AC-06 Given** 审核未通过，**When** PM 填原因，**Then** 运营看到原意见；由负责运营补说明在原记录复审或明确结束；复审不限次、不自行换审核人，保留审核历史（FR-008，已确认）。
3. **AC-07 Given** 已正式对客报价，**When** PM 登记客户还价、运营提交达人回价，**Then** 两侧金额不互相覆盖，反馈关联对应轮次，登记客户还价后立即转达人侧议价，正式提交达人回价后立即转负责PM；正式报价不设固定轮数上限（FR-009/010，已确认）。
4. **AC-08 Given** 已有方案及确认，**When** 授权人员变更合作条件，**Then** 保留旧版并要求重新确认受影响条件，不能使用旧确认直接成单（FR-011）。

5. **AC-28 Given** 同一运营提报已多次复审或正式报价，**When** 继续补说明复审或正式报价，**Then** 不受固定次数/三轮上限阻止、不自行换审核人，历史记录仍保留；仅保存未正式提交的内容不冒充正式回价移交（FR-008/010）。
6. **AC-29 Given** 有旧版成交确认，**When** 运营实质变更平台/类型/权益或PM修改本人自提方案，**Then** 旧成交确认失效，运营路径重新审核、PM自提免审核；已确认的视频条数补正例外仍不增加PM再审（FR-011）。

### User Story 3 - 授权人员生成完整且唯一的订单 (Priority: P1)

客户与达人接受最终合作条件后，授权人员建单，提报以已成单结束，订单及必要视频关联可追溯。
**Why this priority**: 明确本轮终点，防止重复订单与金额错误。
**Independent Test**: 使用已完成最终确认的测试提报创建含两条原创视频的订单，核对数量、两侧金额和终态。
**Acceptance Scenarios**:

1. **AC-09 Given** 同一最终方案及合法金额已满足确认条件，**When** 授权人员建单，**Then** 只生成一个关联订单，提报显示已生成订单并保留可查（FR-012/013）。
2. **AC-10 Given** 建单人无权、缺客户确认或确认属于旧版本，**When** 建单，**Then** 拒绝且不新增订单、视频或部分确认（FR-012/016）。
3. **AC-11 Given** 总数量为 2、双方总价分别为 100.01 与 150.01 的同币种方案，**When** 建单，**Then** 默认达人侧为50.01/50.00、客户侧为75.01/75.00；允许负责方手动拆分自己一侧且合计精确一致；分发不额外增加原创视频（FR-013/014，已确认）。
4. **AC-27 Given** 当前方案客户接受价低于最终达人价且双方总额合法，**When** 负责人确认合作并建单，**Then** 明确提示负Margin及对应金额，但不阻止成单；金额为空、非正、超过两位小数或币种不一致时拒绝且不改写已保存结果（FR-013）。
5. **AC-30 Given** 一方尝试改另一侧拆分或拆分合计不等于对应总额，**When** 保存或建单，**Then** 拒绝；负责运营只拆达人侧、审核PM只拆客户侧，PM自提可拆本人记录两侧（FR-009/013/014/017）。
6. **AC-12 Given** 已成单，**When** 刷新、重试建单或修改其他视频进度，**Then** 返回原订单或明确已成单，不新增；提报不退回议价或随视频流转（FR-012/015）。

### User Story 4 - 多人可靠协作且不越权 (Priority: P1)

测试管理员提供身份与权限，不同同事在各自会话操作共享记录，失败与冲突不损坏已保存结果。
**Why this priority**: 这是用户明确要求的业务测试形态。
**Independent Test**: 运营 A、审核 PM、无权运营 B 使用独立会话，同一测试记录执行读写与冲突检查。
**Acceptance Scenarios**:

1. **AC-13 Given** A 成功提交，**When** PM 刷新，再退出重新登录，**Then** 读取同一已保存记录；不依赖 A 的浏览器或会话继续打开（FR-001）。
2. **AC-14 Given** B 无记录权限，**When** 搜索、打开记录或直接尝试审核/改价/建单，**Then** 拒绝相应操作，不返回未授权报价；修改浏览器身份声明无效（FR-001/017）。
3. **AC-15 Given** 两人打开同一旧版本，**When** 一人先保存而另一人再提交冲突修改，**Then** 后者收到冲突提示，原输入保留，先保存结果不被静默覆盖，须核对后重试（FR-018）。
4. **AC-16 Given** 同一提报被并发或重复建单 10 次，**When** 请求完成并重新查询，**Then** 只有一个订单及一组对应视频；结果不明时能查询原结果再重试（FR-019）。
5. **AC-17 Given** 操作保存失败、会话失效或建单中断，**When** 重新查看，**Then** 无虚假成功；输入可核对重试，建单结果为完整一组或无新增，不留半成品（FR-016/019）。
6. **AC-18 Given** 隔离测试账号和记录，**When** 完成全流程，**Then** 所有新记录和身份限于测试范围，正式记录与配置无变化（FR-020）。
7. **AC-23 Given** 管理员能查看全部测试业务，**When** 尝试代提报、审核、报价或建单，**Then** 写操作被拒绝；直属 PM 可查看直属业务及双方金额，但审核/报价/建单被拒绝；非归属同事不能读取他人明细（FR-002/007/009/012/017，角色边界已确认）。
8. **AC-24 Given** 用户指定测试管理员和测试人员名单，**When** 管理员分配或收回角色/项目权限，**Then** 只有获分配人员能在对应记录范围操作，人员不能自行提升角色；权限收回后不再允许原写操作，历史操作者不改写（FR-017，管理责任已确认）。

### User Story 5 - PM 提报自己的达人 (Priority: P1)

PM 本人提报自己的达人，跳过提报审核，直接填写达人价与对客价（已确认）。
**Why this priority**: PM 自提也是首轮核心业务入口，不能强制其借运营身份或自审。
**Independent Test**: PM A 创建本人提报、填写双方报价并重新登录检查结果。
**Acceptance Scenarios**:

1. **AC-19 Given** PM 本人提报自己的达人，**When** 填写并保存达人价及对客价，**Then** 不需提报审核动作，不伪造审核通过记录，两侧金额分别保留（FR-021）。
2. **AC-20 Given** PM A 自提记录，**When** A 修改双方报价，**Then** 不因 PM 身份禁止填写本人达人价；不据此允许修改其他运营的达人价（FR-009/021）。
3. **AC-21 Given** PM 自提已保存双方报价，**When** 尚未正式报价或缺少当前方案的客户接受/达人确认，**Then** 不能建单；由该 PM 正式对客报价、登记客户接受并确认达人接受后建单，不转交运营、不把免审核当成交（FR-012/021，已确认）。
4. **AC-22 Given** PM 本人自提的订单及视频，**When** 执行现有 Brief、脚本、成片、发布和最终验收流程，**Then** 本人可处理至完成，已完成视频仍只读；这项权利不授予其对其他运营记录的提交、发布或建单权，不重做视频流程（FR-021，责任及隔离边界已确认）。

### Edge Cases

- 同达人同项目有在途正式提报，无论是否已有历史订单均拦截再次提交；不同人草稿不互相覆盖或互相阻止；多负责人/缺失归属证据不得猜测唯一归属。
- 审核 PM 不在有效名单、操作者停用/权限被收回：操作时重新核对，不因之前页面有按钮而接受操作。
- 金额为空不视为零；非数值、负数、非法精度、币种不一致拒绝；总额须大于0且最多两位小数；客户价低于达人价时明确提示负Margin但不阻止确认或建单。
- 最新客户还价不等于客户接受；对客报价不等于成交价；不得通过状态名称推造双方确认。
- 提交后编辑资料不覆盖提交时快照；旧记录没有快照则说明缺失，不补造。
- 方案修改后旧报价/确认仍可追溯，但不能误当新版本的有效确认。
- 网络中断时建单可能已成功：显示结果待核实，不让重复点击生成另一组订单。
- 关闭/离开有未保存内容时提供保存、放弃、继续编辑选择；保存失败继续保留当前输入（建议）。
- 已成单数据改价、撤单、人员交接不是本轮普通操作；旧相关入口需在第 4 步评估隔离，不在此轮顺带实施。
